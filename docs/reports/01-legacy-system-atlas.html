01 / OVERVIEW

What HalalGoes is

A four-sided food-delivery marketplace — customers, riders, restaurants, and an admin back-office — built around a single NestJS backend where nearly every operation is a Temporal workflow. Orders flow through a saga; realtime updates ride a raw WebSocket; rider dispatch runs on PostGIS geo-queries. The platform is functional but visibly mid-migration and MVP-grade, with two findings that dominate everything else: the published backend is not the one the apps actually talk to, and there is no authentication anywhere in the code that is public.

The client surfaces

Customers use an Expo app (onboarding → phone-OTP → feed → cart → checkout → live order tracking on a map → rating). Riders use the "HalalGoes Captain" Expo app (KYC onboarding via presigned uploads → go-online toggle → GPS streaming → order offers over WebSocket → delivery states). Restaurants have two generations: a legacy Expo registration funnel and the current Next.js restaurant-web portal (menu CRUD + live order accept/reject). Admin is a Next.js dashboard for approvals, documents, users, and analytics.

The backend spine

One NestJS process hosts ten feature modules and registers a Temporal worker per module. Checkout is a saga that spawns child workflows for payment (mocked Stripe), order creation, restaurant notification, expanding-radius rider search, and a 5-hour order-tracking workflow. State lives in PostgreSQL 17 + PostGIS (via Prisma) for durable data and Redis for presence, geo, and workflow-address-book mappings. MinIO provides object storage; a full Temporal server stack runs alongside.

02 / TOPOLOGY

System topology

Every service runs on one static-IP Docker bridge network (172.21.0.0/16). The API container exposes REST on :3456 and a raw WebSocket on :9080 in the same process — which is why splitting the Temporal worker out would silently break WebSocket delivery.

Inside the frontend monorepo

The users and rider Expo apps and the two Next.js portals are the live product. The restaurant Expo app is a superseded registration funnel that posts to a Payload CMS and never touches the backend. apps/web and apps/docs are unmodified create-turbo scaffolds (one even renders a stray literal "hello" in its body) that still consume CI time. Of the shared packages, only @halal-goes/auth is real product code — a phone-OTP SDK — but its shared store is broken and every app works around it with a duplicate; @halal-goes/tailwind-config is a literally empty preset.

04 / ORDER LIFECYCLE

The order, end to end

Checkout is a Temporal saga inside a single process. Its workflow ID is the checkout ID, and stateless REST endpoints signal it back through short-lived Redis "address-book" keys. Here is the real path the code takes.

1

Cart & pricing

Client builds a server-authoritative cart (PUT /carts/:userId) and is meant to fetch GET /pricing/:cartId before checkout.

cart-queuepricing-queuebug: pricing feeds a cartId into an Order lookup → never resolves
2

Checkout saga starts

PUT /orders/checkout/:cartId emits an EventEmitter event → initiateCheckoutWorkflow (15-min timeout). The workflow ID doubles as the checkout ID.

checkouts-queuecharges the client-supplied price verbatim
3

Payment + order creation

Child workflows run payment (mocked Stripe — stripe_<nanoid> rows) and order creation, each signaling back via paymentResponse / orderResponse. Order is written straight to CONFIRMED.

payments-queueorders-queueline items drop variants & addons
4

Restaurant acceptance

Restaurant gets an order_request over WS (1-min expiry). PUT /restaurants/:id/orders/:id?action=accept resolves a Redis mapping and signals the saga with restaurantResponse.

order_checkout_mapping:{orderId}:{restaurantId}TTL 30m
5

Rider assignment

orderAssignmentWorkflow searches PostGIS ST_DWithin on rider coords at 5/10/15/20 km, notifies connected riders over WS, and waits for the first accept.

riders-queuenotifications-queuefirst reject cancels & refunds the whole order
6

Live tracking

orderTrackingWorkflow (order-tracking-{orderId}, 5-hour timeout) exposes two Temporal updates — orderStatusUpdate and riderLocationUpdate — driven by restaurant/rider REST calls and broadcast as order_update to the order's WS room.

subscriptions:order:{orderId}rider GPS every 10–15s
7

Delivery & rating

Rider walks PICKED_UP → ON_THE_WAY → DELIVERED. The rating screen exists and the /ratings endpoints work, but the app's submission is a // TODO.

rider earnings never creditedavailability never restored after delivery

The 11-state order status enum (PENDING → PLACED → CONFIRMED → PREPARING → RIDER_ASSIGNED → PICKED_UP → ON_THE_WAY → DELIVERED, plus REJECTED/CANCELLED/DISPUTED) is documented, but because orders are created directly at CONFIRMED, the PLACED and restaurant-prep states are unreachable through the tracking path. The COMPREHENSIVE_ORDER_FLOW_DOCUMENTATION.md in hg-api is the accurate reference; the hg-docker integration guide diverges (it claims a 2-minute restaurant timeout that doesn't exist).

05 / REALTIME & DISPATCH

How realtime actually works

Two subsystems that look Redis-driven in the docs turn out to run differently in the code. The fleet resolved both contradictions.

Dispatch discovery is PostGIS, not Redis

Rider discovery for dispatch is exclusively ST_DWithin on rider.coords with expanding radii. The notification module's Redis GEO fallback (riders:available:locations, riders:available:online) is dead code — nothing on any live path ever writes those keys, so the fallback iterates permanently empty sets. The real geo pool is an undocumented riders:active set used only by the REST "nearby" search.

Delivery is a direct socket scan

Order offers aren't broadcast to channels — the gateway scans in-memory WS clients by userId + userType and emits order_request directly. The rider app's three guessed channel joins (riders, rider:{id}, notifications:{id}) are all ignored by the server; only connect_user and the post-accept join of order:{orderId} matter.

Broken offline path

Queued restaurant offers are never delivered

Offline restaurant offers are pushed to failed_notifications:restaurant:{id}, which has zero readers, while reconnect drains a different key (queue:restaurant:{id}). Riders have no offline queue at all. Meanwhile the saga is told queued:true and waits on a response that can never come.

Split-brain

Accepted orders can strand with a dead workflow

If notification_workflow:{orderId} has expired when a rider accepts, the DB is already RIDER_ASSIGNED but the riderAcceptance signal never fires — the assignment workflow dies on its timeout without running its cancel/refund path. Accept also never flips is_accepting_orders=false, so a rider mid-delivery stays in the dispatch pool.

06 / THE CENTRAL FINDING

There are two backends

The published hg-api is not the backend the apps talk to

Git forensics are conclusive: the rider app was calling http://api.halalgoes.com/riders on 2025-09-30, five days before hg-api's first commit, and the frontends kept integrating new backend surface for 116 days after hg-api went silent. Around 60 endpoints the apps call — the entire /auth/* family, all onboarding flows, admin refunds/disputes/settlements, Stripe Connect — exist in no hg-api commit or API collection. The production backend at api.halalgoes.com is a private, richer continuation of a pre-squash ancestor; the repo you have is a snapshot published (most plausibly) for the frontend agency.

This makes the contract-drift map essential reading: what the apps call vs. what the public backend actually implements.

07 / CRITICAL FINDINGS

What needs attention

Ranked by blast radius. Security exposures first — several are live-credential leaks that persist in git history and require rotation, not just deletion.

Critical

No authentication anywhere in the public backend

Zero guards, middleware, or JWT verification across all of hg-api/api/src. Bearer tokens the apps send are ignored. POST /admin mints an admin with an empty body; DELETE /admin/users/:id and refunds are world-callable; the WS gateway trusts client-declared userId/userType ("MVP mode"), so anyone can impersonate any actor or join any order channel carrying customer PII. better-auth is a dependency that is never imported.

hg-api/api/src · notifications.gateway.ts · admin.controller.ts
Critical

Live MinIO credentials committed in cleartext

hg-api/minio/.minio.sys is real runtime state accidentally committed and pushed. It leaks, unencrypted, an IAM user with a weak secret plus two service accounts with 40-char keys — one a child of root admin@halalgoes.com whose session policy grants admin:* / kms:* / s3:*. These are permanent leaks in git history and must be rotated.

hg-api/minio/.minio.sys · commit 86c52a7
Critical

Rider identity-document bucket is world-readable and writable

The only application bucket ever created — riders, holding rider identity documents — has a public policy (Principal AWS:* → anonymous Get/Put/Delete/List). Anyone can read or overwrite KYC documents. (The doc buckets named elsewhere — profile-pictures, food-images — were never actually created.)

MinIO runtime state · bucket "riders"
Critical

Checkout charges the client-supplied price

The payment workflow charges pricing.amount_to_pay straight from the request body; the server never recomputes it — a pay-what-you-want hole. And because GET /pricing/:cartId is broken (it looks up an Order by the cart ID), the users app's pricing stays at its all-zero default, so in practice every order persists client-fabricated zero monetary fields.

payments workflow · pricing.activities.ts · order.activities.ts
High

Hardcoded Google Maps API keys & secrets in the apps

A Google Maps key is committed in app.json across the users and rider apps and in restaurant-web source; a Directions key is repeated in three rider files. admin-web ships a dead Supabase project URL + anon-key JWT. JWTs are stored in plain AsyncStorage/localStorage and non-HttpOnly cookies. Staging IP 98.130.76.223 and a LAN IP leak into env examples and code.

apps/users · apps/rider · apps/restaurant-web · apps/admin-web
High

Payments are entirely mocked; refunds are TODO logs

No real gateway integration exists — PaymentLog rows get stripe_<nanoid> IDs. Refunds in the no-rider and 5-hour-timeout cancellation paths are literally "Payment refund would be initiated here" log statements. A restaurant rejection where compensation partially fails falls through to rider assignment anyway.

payment.activities.ts · order-assignment / order-tracking activities
High

Geo split-brain stalls orders for new restaurants

Restaurants are created writing a legacy location POINT column, but rider assignment reads only the newer PostGIS coords column (written solely by a separate location PUT). So a POST-created restaurant is discoverable and priceable but its orders stall at rider dispatch with "Restaurant location not found."

restaurants.service.ts · order-assignment.activities.ts
High

Money is lost between cart, pricing, and order

Cart valuation adds a variant price to the base; order creation uses the variant price instead of the base. OrderFoodItems has a unique (order_id, food_item_id) and no variant/addon columns, so addon charges are dropped and two rows of the same item with different variants abort order creation. The coupon calc inverts discount vs. amount-after-discount.

carts / pricing / orders services · schema.prisma
Quality

Redis Sentinel HA is provisioned but broken and unused

Two sentinels with quorum 2 can't tolerate a single sentinel failure; sentinel-2's healthcheck pings the wrong port; redis-master has no data volume despite appendonly yes. In hg-docker the redis.conf bind-mount path is wrong, so the master gets an empty config. The API connects to redis-master directly with REDIS_USE_SENTINEL unset — the whole HA tier is unused.

docker-compose.yml · redis/master/redis.conf
Quality

Large dead-code and mock surface across all repos

MinIO module registration commented out; empty stub services for redis-streams and temporal; /health doesn't exist so the container healthcheck never passes; the users app's legacy React-Navigation entry, dead contexts, and committed vim swap files; restaurant/rider mock timers that fake arrivals and invent earnings; admin-web order UI running entirely on mock PKR data; apps/web + apps/docs untouched scaffolds. Four regional configs (Canada +1, India +91, Dubai, Malaysia) coexist — the live web flow points at Malaysia.

08 / DATA & STACK

Data model & stack reference

Persistence

An 834-line Prisma schema: 27 models, 6 enums on PostgreSQL 17 + PostGIS with 11 extensions and a deliberately varied index strategy (Hash / BTree / Gin / SpGist / Brin / Gist). Soft-delete audit triples (is_deleted / deleted_at / deleted_by) sit on most aggregates. Identity is phone-first (unique phone, non-unique email). Riders and restaurant addresses carry dual geo columns mid-migration. Quirks baked into migrations: a contains_diary typo (for "dairy"), fee defaults hardcoded in the schema (delivery_fee 9.99, platform_fee 4.99), and an Admin model with only id + timestamps — no credentials.

Redis key registry

Redis is the realtime store. Presence sets (users:online, riders:active, restaurants:accepting) with ~2h TTL; the workflow address book (order_checkout_mapping:{orderId}:{restaurantId}, order_rider_checkout_mapping:*, notification_workflow:{orderId}, TTL 30m); order-room membership (subscriptions:order:{orderId}); and a priority-scored offline notification queue (queue:{type}:{id} zsets, scores urgent 1000 / high 500 / normal 100 / low 10, 7-day TTL). REDIS_DATA_STRUCTURE.md documents ~20 patterns — several of which the live flow never populates.
