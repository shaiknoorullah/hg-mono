Foundation, contract & backend

Specification & contract — 100%

The spec of record is closed: 198 features / 10,525 lines across platform, admin, restaurant, customer, rider — each SOW-traced, versioned V0 (43, "one real paid order end-to-end") / V1 (73) / V2–V3 (82). The API contract is the single source of truth: 152 operations in openapi.yaml (matches target exactly), a WebSocket companion, and 330+ fixtures covering every state. The generated @hg/api-client is emitted from it (hand-editing forbidden and enforced).

Design system — 95%

77 shared components (43 web · 34 native) across primitives, content, feedback, navigation, certification and data. This session's foundation landed clean: the Solar Icon primitive, the bespoke HalalShield, the glass adaptive nav (BottomNav native / SideNav web), Plus Jakarta font wiring, and a regenerable token layer. The L-4 lint ("no solid green outside the halal namespace") is live in both stacks. Minor: two token-JSON sources (design-tokens build input vs the richer docs spec) should be reconciled or documented.

Backend (Go modular monolith) — 95%

All planned domains exist, are routed live in main.go, and are exercised by a real harness — not stubs. 20 internal packages (auth, session, account, addresses, catalog, orders, payments, dispatch, rider, restaurant, admin, notify, realtime, handoff, files, httpx, store, system, config).

Proven correct

  • 152/152 contract conformance (enforced floor in spec_test.go)
  • 18/18 invariants: server-prices-order, deny-by-default, deadline_at, authorise→capture/void, ledger SUM=0, atomic notify-in-tx
  • Full stack boots healthy from an empty volume; migrations 0→27 clean
  • Transactional notifications = River outbox, enqueued inside the order tx (genuinely atomic, verified in code)

The ~5% gap

  • Incremental adoption of generated contract types per handler

⚑ Notable finding — the handoff / QR chain-of-custody has no frontend

The backend built the signed-QR seal chain — bindPackageSeal · scanPickup · scanDelivery · reportTamper (4 contract ops, EdDSA-signed, nonce-replay-rejected). No app calls any of them. The rider delivers via plain assignment transitions + a 4-digit OTP / drop-photo POD, which works but bypasses the seal chain the backend implemented. The status doc's "rider: QR scan (handoff)" line overstates what's in code — only POD-OTP is real. This is a genuine functional gap, and it's what pulls the rider app to 70%.

Decision needed: build the rider scan surface + restaurant seal-bind screen (closes the gap), or formally descope QR-seal to v1.1 and rely on the working OTP/photo POD for launch.

Holds in code

  • A-15 seven-check halal instrument wired end-to-end (admin)
  • Real KYC presign-upload flow (restaurant onboarding, rider docs)

  • Admin order-detail live map (needs VITE_MAPBOX_TOKEN in browser — verified earlier this session)
