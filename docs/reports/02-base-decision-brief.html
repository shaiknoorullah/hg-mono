01 / VERDICT

Three decisions, three answers

The request bundles three distinct calls. Separating them is the key to the recommendation: the direction is right, but this specific repo is a pattern library to harvest — not a turnkey base to fork.

Consolidate all HalalGoes projects into one hg-mono monorepo?
Strongly yes

It structurally cures the platform's worst disease — frontend↔backend contract drift.

Rewrite the backend as Go microservices, contracts-first, under strict TDD?
Yes, sound

Right call — but the template gives you the harness, not the enforcement. TDD gates are yours to add.

Adopt ts-monorepo-template as a turnkey base and build on it?
No — harvest it

Impressive design artifact, immature foundation. Copy the proven substrate into a fresh repo.

The one-line recommendation

Start a clean hg-mono with honest git history and CI you trust; harvest the template's contracts pipeline, Nx polyglot graph, Dockerfiles, compose infra, and Helm lib-chart; leave its multi-tenant SaaS spine and hollow platform-product layers behind; and wire strict-TDD enforcement before the first line of domain code.

02 / WHY A MONOREPO

The monorepo fixes what broke HalalGoes

Independent of which base you pick, consolidation is the right move — because the atlas's single worst finding is a direct consequence of splitting frontend and backend across repos.

HalalGoes shipped two backends: the apps call ~60 endpoints that don't exist in the published API, with silent payload mismatches like {is_accepting} vs {isAccepting}. That happened because the only "contract" between repos was a hand-maintained Hoppscotch collection that drifted.

The template's buf-based cross-language contracts pipeline is the exact antidote — and it's the one component all four agents independently rated genuinely excellent. A single .proto source generates typed Go servers and TS / React Native clients together, with a CI drift gate that fails the build when generated code and committed code diverge. In a monorepo, the two-backends failure becomes structurally impossible. That alone justifies the direction.

05 / TAKE · LEAVE · BUILD

What to harvest, drop, and build

Take (harvest)

  • Contracts pipeline — buf + contracts-codegen.yml drift gate. The reason to adopt anything.
  • Nx polyglot graph — @nx-go, @nxlv/python, @monodon/rust + cache config.
  • go-hello as the Go reference (chi, pgx/v5, kafka-go, zerolog, prometheus, OTLP, testcontainers).
  • Dockerfile templates (distroless multi-stage) + cosign keyless-signing workflow.
  • Compose data-plane — Postgres HA, Redis, Kafka KRaft, Debezium, OTel collector.
  • Helm lib-chart + the 3-file per-app chart pattern.
  • Dev-verb CLI patterns + tooling (ESLint, changesets, lefthook, commitlint).
  • Design specs for data-eventing / event-journal / saga — as guidance.

Leave (drop)

  • Multi-tenant SaaS spine — tenancy-client, config/tenants, x-tenant, edge router. Subtractive tax for a single marketplace (keep only per-tenant theming → per-restaurant branding).
  • 5-profile system + Crossplane/Kargo/ArgoCD/7-cloud Terraform — huge, mostly stubbed. Pick one deploy target.
  • Platform-product features — MCP server (8/18 tools stubbed), genesis-only audit chain, recommender/cost-simulator.
  • Existing AGENTS.md / CLAUDE.md / ADR docs — rewrite from scratch; the current ones mislead.
  • Payload CMS — unless you truly want self-hosted CMS for menus/marketing.

Build (greenfield)

  • The delivery domain — orders, menu, cart, checkout saga, geo dispatch, ratings.
  • Go golden path — service template + real repo new service scaffolder.
  • gRPC serving + interceptors (auth, tracing) and shared Go libs (pgx+PostGIS, redis, kafka, OTel middleware+metrics, logging).
  • Outbox / eventing — before payments; kill the dual-write.
  • Realtime layer (WebSocket/SSE) for order tracking.
  • Auth — phone-OTP + JWT + multi-role onboarding/KYC with private object storage.
  • Payments (mock → Stripe Connect), push notifications, rider app + restaurant portal.
  • TDD enforcement — per-language coverage gates (esp. Go), diff-coverage required check, integration tests in CI, lint warnings→errors, branch-protection-as-code.
06 / PHASED PLAN

A sequence that de-risks the hard parts

Phase 0days

Trustworthy skeleton first

Stand up hg-mono from harvested substrate. Fix the CI blockers (Go toolchain absent in CI, version drift 1.24 vs 1.25, boot-blocking required-but-unused REDIS_URL). Wire strict-TDD gates now — coverage + diff-coverage required checks — so tests-first is non-optional from commit 1. Write honest agent docs.

Phase 1weeks

Contracts-first + one bounded context

Model the domain in proto and generate Go + TS. Build the shared Go libs and the golden-path service template. Port one context end-to-end under TDD (identity or catalog) as the reference pattern everything else copies.

Phase 2weeks→months

The hard cores, under TDD

Build checkout saga (Temporal, done right), geo dispatch, realtime tracking, and outbox/eventing. These are exactly HalalGoes' buggiest areas — TDD here pays for itself immediately.

Phase 3weeks

Frontends into the monorepo

Move the apps in to consume generated clients (this is what kills the drift for good). Add the missing rider app and restaurant portal. Wire payments and auth/KYC properly.

Phase 4—

Finish one deploy path

Pick a single target and make it actually bring up + smoke-pass. Skip the 5-profile matrix until there's a reason for it.

Don't port the bugs

A rewrite is the chance to fix the atlas's criticals by construction: auth enforced at a gateway interceptor (not absent), server-authoritative pricing (not client-supplied), private KYC buckets (not world-readable), rotated secrets (not committed). Bake these into the contracts and the golden-path template so they can't regress.

07 / RISKS TO MANAGE

What to watch if you proceed

Hollow CI undermining TDD

If any harvested workflow passes without asserting, it poisons the tests-first premise. Delete or de-stub every no-op verb before trusting the pipeline.

Doc drift corrupting AI-assisted work

The template's agent docs describe the wrong repo. Rewrite AGENTS.md to match reality on day one, or every agent you run will inherit false assumptions.

Multi-tenant tax

The base's strongest opinion is tenant-per-subdomain SaaS. For a single marketplace it's overhead to strip — budget for the subtraction, don't leave it half-wired.

Go is second-class today

No generator, no CI build, gRPC not served, no shared Go libs. Your primary language needs the most net-new substrate — plan for it, don't assume the template covers it.

License inconsistency

MIT at the root vs Apache-2.0 in Cargo.toml. Resolve before harvesting code into a repo you'll distribute or open-source.
