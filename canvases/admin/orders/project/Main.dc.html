Orders and refunds

Find any order, see exactly where it stands and what money moved, and act on it: cancel, reveal the delivery address with a reason, or refund by reason with the split the server computes. Everything drawn as real comes from the API contract. Anything the contract lacks is a labelled placeholder.

How every working page is laid out

  • The page never scrolls. Each board is the whole 1440 × 900 window. Long lists scroll inside their own region (the grid virtualises its rows); the page stays still.
  • Overview, then detail, then more detail, side by side. Orders grid or Disputes → the list you came from + order + More detail (timeline, map, event log, ledger). The Refunds page is for its own work only: the failed-refunds queue and looking up a code.
  • No dialogs for working tasks. Cancel, reveal the address and issuing a refund (form, review and result) open as an in-page panel that takes the place of More detail; Close or Done brings More detail back. The live map widens More detail over the list. Sign in again is the one dialog, because nothing can continue without it.
  • Collapsible navigation and panes. The sidebar folds to an icon rail when an order is open; the list and More detail panes collapse or widen.

Owner decisions drawn here

  • Cancel works at launch with an optional case id, before and after the restaurant accepts. Support agents cancel only before acceptance. The contract still requires a case id (Needs API).
  • No package seals at launch. No seal step on the timeline; the packaging-tamper refund reason isn't offered. Staff file a customer's halal complaint as Halal concern, with evidence. The restaurant pays only when the evidence backs it up; otherwise it is goodwill paid by the platform.
  • A goodwill refund above $50.00 needs a second approver, for every role.
  • Dates: short in table cells (28 Sep, 6:52 pm), the full date in the tooltip and on detail views.
  • Expiring soon shows its amber tint, never the solid seal, labelled with the certificate’s own date: Drawn with the proposed HalalState composite (Proposed component: HalalState) until the design system’s badge has this look.
  • No recovery codes: a lost authenticator is reset only by a super admin, after calling the person back on the phone number on file and matching two account details.
  • Later-version features are out: rider ratings and My sessions. Staff management and the menu review queue now ship at launch (owner decision, round 2), on their own canvases.
  • Light theme only for release 1.0 (owner decision); the dark boards are gone.
  • Times are 12-hour everywhere (6:52 pm).
  • On-call for failed refunds is named with a phone number and links the runbook from issue #66 (name and phone to come).

Needs API (to file)

  • Cancel: make the case id optional (owner approved); which refund reason each cancel reason becomes.
  • Support cases: handing a cancel to an admin, opening an incident mid-delivery, noting refunds against a dispute.
  • Disputes: reason in the list, evidence, resolving with Dispute resolution, escalation count and history, server sort by deadline, and whether automatic resolution refunds.
  • Card chargebacks on the admin order view: disputed amount, evidence deadline, evidence sent, payout holds.
  • Refunds: Fees only on the staff refund route, with a case id (the staff route has no Fees only scope; the general refund route has it but carries no case id or reason text); an upload purpose for refund evidence, and evidence ids on the staff route; refunded quantity per line; Whole order after a partial refund; order code and requester on each refund; replaced-by link; the grievance a Halal concern opens; preview and breakdown; 24-hour limit left; step-up code.
  • Approval requests: read on the order, list, approve, decline.
  • Order view: reassigning a delivery to another rider by hand, including when a rider is suspended mid-delivery (owner decision, round 2); customer name and masked phone; restaurant phone, address and preparation estimate; rider phone or proxy and account id; pickup estimate; click-to-call; staff audit events; halal state at the time of the order.
  • Grid: restaurant picker by name; search by phone, email or name (issue #148); time in state; a sort parameter.
  • Map and privacy: a coarse destination while the address is masked, and the exact destination kept out of the masked view.
  • Alerts: history, acknowledge, order code and severity on every event.
  • Other: staff name and email on the session; an incident record for ledger mismatches.

What these screens hold to

Money is the server's. Every amount is integer cents in CAD from the API, drawn by Price. Nothing is added, split or estimated here. No tax is charged while HST registration is open, so orders show only the quote's lines, which add up to the total, and the ledger has no tax postings; every batch sums to zero. Halal is never guessed. Admin screens use the operational badge. A missing field shows plain "No status on file", never a badge. Expired is slate, never red. Expiring soon is amber, labelled with its certificate’s date (“Halal certified · expires 19 Oct”), drawn with the proposed HalalState composite. Solid green is the seal alone. Don't invite the wrong action. Where the system will cancel and refund on its own, refund and cancel sit in More actions and the page says so. A disputed order says refunding won't close the dispute. Role-aware. A support agent never sees a control the server would refuse, or sees it off with the reason. Nothing is lost. A failed action says "Nothing was changed". A session that ends mid-form keeps the draft in its panel. Plain words. No raw codes or protocol terms in copy. Codes and ids in IBM Plex Mono.
